# PRD 需求详情写作模板

单一来源声明：本文件是功能需求详情写作模板、信息分级、反例和单元格段落写法的唯一来源；权威文档骨架见 `prd-schema.lock.md`，字段说明见 `prd_schema.md`，完整工作流和三档出稿定义见 `../SKILL.md` 的“出稿状态与流程”。

关键禁令摘要：正文不得出现生成来源痕迹、本地路径、内部编号或编造负责人；截图必须真实或明确标注待补；字段来自配置时必须映射管理端。完整规则以 `../SKILL.md` 为准。

## 核心原则

PRD 不是设计稿翻译稿。截图负责说明“长什么样”，正文只补“截图看不出的业务逻辑”。

PRD Forge 写作规则：需求描述要像产品负责人写给研发和协同方看的规则说明，而不是页面说明书。每一句正文开头用关键词做抓手，复杂需求用编号和缩进拆开。

## 信息分级

| 等级 | 内容类型 | 写法 |
|------|----------|------|
| L0 | 一眼可懂：按钮文案、模块标题、视觉层级、普通列表展示 | 不写，交给截图 |
| L1 | 字段口径：数字、标签、状态、榜单值 | 弱写字段来源、取值口径、默认值 |
| L2 | 业务规则：筛选、排序、准入、状态流转、计算公式、次数、余额、库存限制 | 详细写条件到系统行为 |
| L3 | 高风险规则：资金、奖励、风控、人工开奖、异常、跨系统依赖 | 写 AC、异常路径、owner，必要时补对账或风控要求 |

## 信息分级反例

| 错误写法 | 问题 | 正确做法 |
|----------|------|----------|
| “点击按钮后跳转到商详页” | 把普通交互当业务规则写 | 删除，交给截图；除非跳转存在业务条件 |
| “榜单展示用户头像和昵称” | 复述界面可见信息 | 删除或并入字段来源说明 |
| “数字字号 14pt，颜色 #333” | 把视觉规范写进 PRD | 删除，交给设计稿和设计规范 |
| “投入量 = 用户出价 x 倍率” | 计算公式写得过轻 | 升级为 L2，补计算时机、数据源、边界值 |
| “排序按互动量倒序” | 缺少平分规则和触发时机 | 写成“列表加载时，按互动量倒序；互动量相同时按时间倒序” |
| “奖励发放成功后展示弹窗” | 漏写失败和对账 | 补成功 AC、失败重试、超时降级、对账要求 |
| “余额不足时按钮置灰” | 漏写判定口径 | 补判定时机、数据源、点击时二次校验 |
| “商品数量取自接口 A” | 漏写数据源细节和刷新时机 | 写成“商品数量取自接口 A 的 total 字段，进入页时拉取一次，分页切换时重新拉取” |

## 功能模块排版模板

模块标题只写中文业务名。功能需求详情默认使用三列表格：`模块 | 展示 | 需求描述`。

| 模块 | 展示 | 需求描述 |
|------|------|----------|
| 中文模块名 | 最新设计稿真实截图；无法截图时写 `待设计补图` | 使用下方段落结构 |

展示列写 `待设计补图` 时，必须同时在待确认事项表登记缺失原因和负责人，避免兜底变成漏洞。

### 需求描述列段落结构

单元格内必须使用多个段落。禁止把多行内容塞进一个字符串，也禁止在 Word 中显示字面量 `\n`、`<br>` 或 `<br/>`。

每条正文必须先给关键词，再写规则。复杂规则使用子编号和缩进，增强人类扫读效率。

```python
cell = row.cells[2]

def add_p(text, bold=False):
    paragraph = cell.add_paragraph()
    run = paragraph.add_run(text)
    run.bold = bold

add_p("1. 业务目的", bold=True)
add_p("价值定位：让[用户]在[场景]下[达成目标]。")

add_p("2. 验收标准", bold=True)
add_p("1. 触发条件：当[条件]时，系统应[具体行为]。")
add_p("2. 结果校验：当[条件]时，系统应[具体行为]。")

add_p("3. 业务规则", bold=True)
add_p("1. 排序口径：[规则说明]。")
add_p("2. 复用范围：[复用系统和本期改造边界]。")

add_p("4. 数据字段", bold=True)
add_p("1. 字段名：[服务/表/管理端配置]；[取值/计算/截断/默认值]。")

add_p("5. 异常路径", bold=True)
add_p("1. 空数据：[系统行为]。")
add_p("2. 接口超时：[系统行为]。")
```

Node.js `docx` 库的等价写法：每个段落对应一个 `Paragraph`，每段文字对应一个或多个 `TextRun`，由 `TableCell.children` 承载。

### 可选扩展列（多轨 / 依赖矩阵场景）

当需求按方向分组、需要在评审时一眼看清排期依赖时，可在三列后追加扩展列：

`模块 | 展示 | 需求描述 | 是否依赖设计 | 是否依赖外部 | 代码参考（能力级，可选）`

- 是否依赖设计 / 是否依赖外部：填"是 / 否 + 一句话原因"。
- 代码参考：**仅存量优化 / 工程交接型 PRD 启用**，且只写**能力级**描述（复用了哪个现有能力、本期改造点），**不写文件路径、函数 / hook 名或实现细节**（遵守 `../SKILL.md` 出稿流程第 3 条与 `prd-rationale-vs-implementation.md`）；对外 / 正式 PRD 省略此列。

扩展列为可选项，不改变既有三列与信息分级规则。分方向版式、总览表与编号规则见 `prd-direction-layout.md`。

> 单元格呈现：经飞书 CLI 交付的分方向版式 PRD，**默认用 `<ul><li>` 无序列表**；上文「加粗编号小标题」段落写法是**无法获取飞书 CLI 权限**（如产出 docx）时的降级写法。两者都禁止字面 `<br/>` / `\n`。详见 `prd-direction-layout.md`。

## 写作边界

- 不写按钮位置、颜色、间距、动效、普通点击跳转；除非该交互影响业务规则、风控或验收。
- 不使用竖线装饰符作为小标题；统一使用加粗编号标题。
- 功能需求详情的模块列禁止写负责人、团队、优先级。
- 每条 AC、规则、异常路径独立成段，不塞进一个长段落。
- 字段来自管理端配置时，注明“管理端可配置”，并在管理端需求章节映射成配置能力和配置项。

## 业务安全与内容安全

- 业务安全：涉及资产损失、薅羊毛、设备/账号/邀请、任务奖励、兑换、拍卖。
- 内容安全：涉及 UGC 内容、评论、图片、审核、举报、互动内容风险。

两者不要混写。同一模块同时涉及两类风险时，拆成两个需求行或两个子段。
