# PRD 分方向版式（增长 / 优化 / 多轨需求）

适用于「一个目标拆成多条方向、每条方向下挂多个需求点」的 PRD，典型场景：增长活动优化、存量功能迭代、多轨并行需求。本文件只规定**版式与编号骨架**，不重复造写作规则：

- 章节骨架与必备表格 → 以 `prd-schema.lock.md` 为权威；本版式是其**渲染变体**，不覆盖它。
- 信息分级、反例、单元格"写什么" → 以 `writing_templates.md` 为唯一来源；但**单元格"怎么排版"（呈现结构）见「三、需求模块」**，本方法默认飞书 `<ul><li>`。
- 产品需求 vs 实现细节的边界 → 以 `prd-rationale-vs-implementation.md` 为准。

冲突时原则上以上述既有 reference 与 `../SKILL.md` 出稿纪律为准，本文件让步；**唯一例外是单元格呈现结构**——本方法默认用飞书 `<ul><li>` 无序列表（见「三、需求模块」）。

## 何时使用

- 需求可自然归入 2 条以上「方向 / 目标轨」，且每条方向内有多个需求点。
- 需要一张总览表让评审一眼看清"有哪些模块、各属哪个方向、优先级、前后端"。
- 有参考稿（同团队历史 PRD）需要对齐标题与编号风格。

不满足时走 `prd-schema.lock.md` 默认骨架即可，不必套用本版式。

## 版式骨架

三段式，映射到 `prd-schema.lock.md` 的章节：

| 本版式 | 内容 | 映射 lock 章节 |
|---|---|---|
| 一、需求背景 | 数据/漏斗表（`指标 \| 数据 \| 说明`）+ 问题诊断 + 本期目标 | ch2 背景目标 |
| 二、需求概述和优先级 | 全量需求总览表（见下） | ch3 范围（in-scope 增强版） |
| 三、需求模块 | 按方向分组的需求模块表 | ch4 功能需求 |

需要后台需求、实验、埋点、名词解释时，按 `prd-schema.lock.md` 在三之后续接对应章节，不省略。

### 一、需求背景
先用数据表锚定现状（每行一个指标 + 昨日/基线数值 + 一句话说明），再用一段问题诊断点出"问题不在 X 而在 Y"，最后一句话目标。用数据说话，不写空泛背景。

### 二、需求概述和优先级
一张总览表，列：

`方向 | 编号 | 需求模块 | 优先级 | 一句话目标 | 前·后端`

- 是 `prd-schema.lock.md` in-scope 表（`No. | Requirement | Team | Priority`）的增强版：多了"方向"分组、"一句话目标"和"前后端"拆分。
- 编号与「三、需求模块」逐条对应；编号在各方向内独立（见下），靠"方向"列消歧重复编号。

### 三、需求模块
按方向分组：`方向N：<名称>`（一级分组）→ `N、<主题>`（主题）→ `N.M <模块名>（pX）`（挂表的需求点）。每个需求点一张表，沿用 `writing_templates.md` 的功能模块表：

`模块 | 示意图 | 需求描述`（+ 可选扩展列，见下）

单元格呈现**默认用飞书无序列表 `<ul><li>`**：每个要点一个 `<li>`，去掉「1、2、3」内联序号与句末句号，模块名即小标题；要点较多时可加一层加粗小标题分组。**仅当无法获取飞书 CLI 权限**（交付目标非飞书、需产出 docx 等）时，才降级为 `writing_templates.md` 的「加粗编号小标题 + 子编号缩进」段落写法。无论哪种，单元格的信息分级与"写什么"仍以 `writing_templates.md` 为准，且都禁止字面 `<br/>` / `\n` / 竖线小标题（满足 `../SKILL.md` 出稿流程第 4 条的可读段落结构；`<ul><li>` 本身即合规的可读结构）。

## 编号规则

- **每个方向独立从 1 重起**：方向1 用 `1、/1.1`，方向2 也从 `1、/1.1` 开始，方向3 同理。靠"方向"层级与总览表"方向"列消歧。
- 优先级 tag 直接写进挂表标题：`N.M 名称（p0 | p0.5 | p1）`。
- 标题层级镜像参考稿：`一/二/三` + `方向N：` + `N、` + `N.M`。

## 可选扩展列（依赖矩阵）

多轨需求常需在功能模块表三列后追加，便于评审排期：

`… | 是否依赖设计 | 是否依赖外部 | 代码参考（能力级，可选）`

- **是否依赖设计 / 是否依赖外部**：填"是/否 + 一句话"（如"是，需确认入口样式"/"是，需后端下发奖励值"）。
- **代码参考（可选）**：仅当 PRD 用于**存量优化 / 工程交接**时启用，且**只写能力级描述**——"复用了哪个现有能力 / 本期改造点是什么"，**不写文件路径、函数/hook 名、实现细节**（遵守 `../SKILL.md` 出稿流程第 3 条与 `prd-rationale-vs-implementation.md`）。对外 / 正式 PRD **省略此列**。
  - ✅ "复用现有分享弹窗能力，新增首屏常驻入口"
  - ❌ "复用 MainVenueSharePopup，改 HeroSection/index.tsx"（写了内部名与路径）

## 参考稿锚定

成稿前先读一份同团队参考 PRD，提取其标题层级与编号逻辑（几级标题、主题怎么编号、优先级 tag 怎么标），新稿镜像同一套，降低评审的格式陌生感。无参考稿时用本文件骨架。

## 合并同类项（多来源汇总）

把多份来源 PRD 合并为一份时：

1. 按"主题"归并重复需求点，相同主题的描述取并集去重。
2. 保留更可读的结构（分方向 + 嵌套编号 + 总览表），不因合并退回扁平长列表。
3. 显式补回被某一稿裁掉、但确属本期范围的需求点，避免合并造成范围缩水。
4. 合并后统一过一遍信息分级（`writing_templates.md`），删掉 L0 视觉复述，补齐 L2/L3 规则与异常。
