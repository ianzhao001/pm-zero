# Demo 产出铁律

适用边界：遵循当前计划已加载的冻结流程协议与确认范围。快速及六阶段默认正常主流程，空态、异常态及测试仅按用户明确请求纳入；旧项目按原范围。本文 HTML/工作台形态不用于静态阶段交付，局部 HTML 仅作导图中间文件。

## 来源与用途

本文档吸收自 magi-product `lead-pm-prompt.md` 模式 B,用于约束 `design-forge` 生成可交互 Demo 时的复用、拆分、降级和完整性原则。

## B.1 先复制参考文件铁律

- 有参考 Demo 时,先复制参考文件再做最小化改动,不要另起炉灶。
- 保留原有 CSS 变量、间距、字号、颜色和组件风格。
- 除非用户明确要求重构视觉系统,否则不要创建新的设计语言。

## B.2 多 Demo 产出原则

- 车机、手机、Web 等不同端形态应各自独立 HTML。
- 多功能模块彼此差异大时,拆成多个 Demo 文件,避免一个页面承载所有状态。
- 每个 Demo 都应能独立打开和解释,不要依赖外部构建步骤。

## B.3 信息架构降级

- 单功能新增优先放在既有二级入口或弹窗中。
- 不为小功能新增一级 Tab。
- 导航、交互或视觉变更须回当前流程的对应设计阶段确认；快速模式回 S2，模型与高保真联合确认，不补独立交互稿。需求范围变化回 S1。

## B.4 最小化改动

- 继承参考 Demo 的 CSS 变量。
- 继承既有 spacing、radius、shadow、font-size 体系。
- 只改与当前需求直接相关的区域。
- 不顺手优化无关页面,避免 review 范围膨胀。

## B.5 交互完整性

- 弹窗内逻辑必须完整可用,包括正常路径的确认、取消和关闭；错误提示仅在请求范围内实现。
- 列表/详情/弹窗之间的跳转应能形成闭环。
- 覆盖正常核心路径；empty、error 等异常态只在用户明确请求时制作，旧项目按原已确认范围。

## 分批产出规则

满足任一条件时强制分批:

- 模块数 > 3。
- 单个 HTML 预计超过 500 行。
- 同时覆盖多端形态。
- 同时包含主流程、异常流、运营态、管理态。

分批方式:

1. 先产出基础主流程 Demo。
2. 用户明确请求异常态 / 边界态时再产出对应 Demo。
3. 最后产出多端或扩展模块 Demo。
4. 每批都要写清楚本批覆盖范围和未覆盖范围。
